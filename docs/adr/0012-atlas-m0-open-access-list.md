# ADR-0012: Atlas M0 for prod, with an open IP access list

- **Status:** Accepted
- **Date:** 2026-11-19
- **Deciders:** Rishekesh

## Context

Prod needs a MongoDB database at no monthly cost. Atlas M0 is free, runs on AWS in Sydney
(`AP_SOUTHEAST_2`) and is managed by the `mongodb/mongodbatlas` Terraform provider.

M0 is a shared tier: it has no VPC peering and no PrivateLink. The API runs on Fargate in public
subnets with no NAT Gateway (ADR-0010), so each task gets a new public IP on every deploy.
An IP access list can't name those addresses in advance.

Options considered:

- **A. Allow `0.0.0.0/0` and rely on credentials and TLS.** Free; the database endpoint is
  reachable from the internet, but only with a valid user and password over TLS.
- **B. NAT Gateway with a fixed Elastic IP, and allow only that IP.** Tight access list, but about
  US$45/month, more than the whole budget.
- **C. M10 with PrivateLink or peering.** Private networking, but M10 starts around US$57/month.

## Decision

Option A, with these controls:

- The API's database user has `readWrite` on the `inkwell` database only, scoped to this one
  cluster. It can't read or write any other database or administer the project.
- Its password is 32 random letters and digits (~190 bits), generated by Terraform. It lives only
  in the encrypted Terraform state and in Secrets Manager (step 10), never in git or chat.
- Atlas requires TLS on every connection.
- Terraform talks to Atlas through a service account with only Organization Project Creator
  permission. Its credentials are environment variables kept in `~/.inkwell-atlas.env`
  (outside the repo, mode 600).

## Consequences

- The cluster can be reached by anyone on the internet who has the password. A smoke test proved
  the API user can write to `inkwell` and is refused on any other database.
- M0 limits apply: shared CPU, 512 MB storage, no backups. Acceptable for a portfolio app.
- Moving to B or C later is a Terraform change to the access list or cluster tier, not a code change.
- Interview point: when the network can't be the boundary, make identity the boundary
  (least-privilege user, strong secret, TLS) and write down the trade-off.
- A new or changed database user takes about a minute to reach the cluster; the first connection
  right after `apply` failed with "bad auth" and succeeded a minute later.
